Bounded native execution

shield __internal run launches a small set of macOS, GNU/Linux and Windows commands under active policy and records their outcomes. For ordinary Claude or Codex sessions, use native project setup.

The runner uses literal argv, an explicit canonical cwd, and inherited standard streams. It adds no shell or PATH lookup. macOS leaf commands receive only LC_ALL=C; Windows leaves receive only the OS SystemRoot. Git uses the settings below. Start with the supported commands, then run an example.

Supported contract

Executable Arguments
/bin/echo Literal arguments, interpreted by the native echo command
/usr/bin/true None
/usr/bin/false None
/bin/sleep One finite nonnegative decimal number, at most 86400 seconds
/Library/Developer/CommandLineTools/usr/bin/git status, diff, diff --cached, or log -n N with decimal N from 1 to 100

GNU/Linux accepts the same four leaf paths (/bin/echo, /usr/bin/true, /usr/bin/false, /bin/sleep) and argument forms, plus /usr/bin/git version 2.53.0 with the Git forms above. Root-owned distribution symlinks such as a merged /bin resolve to their captured native images. Linux bindings require ELF64 images matching x64 or ARM64, a supported glibc 1.1 loader cache and kernel procfs.

On AMD64 or ARM64 Windows, use an absolute System32 path for system leaves or the protected installation path for Git:

Executable Arguments
hostname.exe None
whoami.exe None
timeout.exe /t N /nobreak, with decimal N from 0 to 86400
<protected Git installation>\ucrt64\bin\git.exe status, diff, diff --cached, or log -n N with decimal N from 1 to 100

On ARM64 use clangarm64 in place of ucrt64. Executables and DLLs must have the native architecture of Shield: AMD64 for its x64 build, ARM64 for its ARM64 build. The ARM64 implementation is accepted for this stage without native runtime tests; this is not an ARM64 acceptance result.

For example, from PowerShell with an enrolled project and a matching active rule:

shield __internal run --project C:\Acme -- "$env:SystemRoot\System32\hostname.exe"

Other executables, scripts, wrappers, PATH names, and argument forms block even if policy allows them. The runner neither enables SDK Bash nor installs an agent integration.

The macOS leaf binding requires canonical root-owned executable and dyld files on the same read-only filesystem as /, without group/other write or set-ID mode. The native Mach-O slice must declare exactly /usr/lib/dyld and /usr/lib/libSystem.B.dylib, without rpaths, embedded dyld environment, custom libraries or unrecognized load commands. File identity, metadata, filesystem read-only state and cwd identity are rechecked at the locked launch handoff. History retains executable and loader digests as binding evidence.

Shield trusts the OS and libSystem/shared cache; it does not verify Apple’s boot seal or hash the full transitive cache. Privileged remounts, OS replacement, and unrestricted external processes are outside its protection. Cwd is passed by pathname after revalidation, so external directory replacement remains possible.

Windows requires canonical project/cwd paths on the OS boot drive, with cwd outside the project’s .shield directory. It holds cwd ancestors against deletion and binds their volume/file identities. System leaves, their declared PE libraries and the loader/API-set baseline must be protected System32 files owned by SYSTEM, Administrators or TrustedInstaller, without ordinary-user write/delete rights. Held file handles deny write/delete sharing; issuance and handoff recheck file identity, ACLs and the recorded digests. The child inherits an explicit System32 DLL search directory and no PATH, preventing project-folder DLL fallback. Shield trusts the protected OS loader, API-set mappings and transitive system libraries; it does not hash every transitive DLL or isolate privileged OS changes. Other drives, network cwd paths and local executable copies remain unsupported.

On GNU/Linux, the executable, glibc interpreter and complete declared library closure must be root-owned regular files without set-ID or group/other write bits, beneath root-owned non-writable-to-other-users directories. Bindings retain open image handles, file identities and digests and revalidate them at handoff. Every executable, interpreter and library path is walked before resolution; symlinks must be root-owned, each traversed directory must be root-owned without group/other write permission, and link chains are retained for comparison. Custom RPATH/RUNPATH, audit/filter/auxiliary loaders, nondefault library search, escaping library names and nonempty /etc/ld.so.preload are refused. A protected empty preload file is retained when present.

The runner uses normal kernel execution, preserving argv[0] and /proc/self/exe. It retains and verifies the root-protected glibc 1.1 loader cache, a native baseline entry for each declared library, and every recorded native variant in the dependency closure. Cache files with unsupported formats, malformed bounds or missing baseline entries are refused. Hardware-variant selection remains the protected OS loader’s responsibility. No LD environment or custom library search is inherited. The kernel, protected system implementation, privileged changes and external cwd replacement remain outside the binding’s guarantees. This is bounded execution, not a sandbox.

Git inspection

On macOS, Git requires Apple’s Command Line Tools Git 2.50.1 (Apple Git-155) at the exact path in the table and an ordinary .git directory at the enrolled project root. Linked worktrees, bare repositories, the /usr/bin/git dispatcher, Xcode/Homebrew Git, aliases, extra flags and other commands are unsupported. Repositories with .git/info/attributes are unsupported.

GNU/Linux Git uses the same fixed inspection arguments and repository capture as macOS, at /usr/bin/git version 2.53.0. The ELF executable and library closure use the Linux binding above. Bare repositories, linked worktrees, commondir, local copies, helpers selected by extra argv and other versions remain refused.

On Windows, Git requires version 2.56.0.windows.3 in a protected ucrt64/bin (AMD64) or clangarm64/bin (ARM64) installation on the OS boot drive. The defaults are C:\Program Files\Git\ucrt64\bin\git.exe and C:\Program Files\Git\clangarm64\bin\git.exe. The cmd/git.exe dispatcher, other versions/layouts, bare repositories and linked worktrees are unsupported. The executable, its four declared application DLLs, helper directory and OS libraries require protected owners/ACLs. Bindings hold the application namespace, image identities/digests, repository directory, main config and HEAD. Git receives ordinary drive paths because it rejects verbatim \\?\ spelling in its environment. Names ending in spaces/dots, DOS devices and alternate streams are refused during that conversion.

Policy and approval match the original executable and arguments. Shield adds fixed launch arguments: no pager, fsmonitor, untracked cache, hooks, automatic maintenance/GC or transport protocols. Status uses short output without untracked files or submodule inspection; diff disables external diff/textconv and submodule inspection; log uses bounded one-line output without signature verification or decoration. These controls follow the Git diff contract. Git has no inherited environment: LC_ALL=C, global/system configuration disabled, optional locks and terminal prompts disabled, lazy fetching disabled, and explicit GIT_DIR/GIT_WORK_TREE fixed to the enrolled repository. System/global attributes are disabled; repository attributes are read from the empty SHA-1 tree instead of working/index attributes, preventing clean/process filters. Diff therefore reports raw working bytes rather than filter-normalized content. These settings use the Git attribute-source contract. Windows also receives SystemRoot and the bound installation’s helper path. Disabled file settings use NUL on Windows and /dev/null on macOS.

Policy evaluates the exact arguments and complete cleared environment that the runner will spawn. For Git, this includes the fixed --no-pager -c ... prefix and inspection suffix above. A rule whose exact arguments are only status therefore does not match the effective Git launch. Review the effective arguments shown in the request before granting permission. The original submitted command is retained as original_input in diagnostic evidence.

Native approvals bind this effective launch and its environment. Historical approvals created without that binding remain inspectable; retrying them requires a fresh request and review.

On macOS the root-owned Git executable and its root-owned, non-writable-to-other-users parent directories are verified. Its native Mach-O contract permits only dyld, libSystem, libz, libiconv, CoreServices and CoreFoundation; the OS libraries/cache remain trusted. The native image must contain the observed version marker; that marker is a compatibility check, not independent publisher authentication. Git executable bytes are rehashed at approval issuance and launch, along with ordinary identity checks. Approvals also bind the repository directory identity, main config and HEAD contents, exact derived launch arguments and settings. Changing those bindings requires a fresh request.

Windows captures executable/application DLL digests at issuance and run preparation, retains handles that deny write/delete sharing, and revalidates identity and ACLs at handoff. It verifies that the submitted executable selects the captured image. The protected OS loader and transitive OS libraries remain trusted. The Windows version marker checks compatibility, without independently authenticating the publisher.

Approval does not freeze working files, the index, refs, included configuration, or objects. Git effects are not fully isolated, and privileged executable changes or external pathname races remain possible.

shield __internal run --project /path/to/acme -- /Library/Developer/CommandLineTools/usr/bin/git status
shield __internal run --project /path/to/acme -- /Library/Developer/CommandLineTools/usr/bin/git log -n 10
shield __internal run --project C:\Acme -- "$env:ProgramFiles\Git\ucrt64\bin\git.exe" status

Run with active policy

Initialize the project using the setup guide. Policy matches the absolute system executable and the exact literal arguments, with the effective canonical cwd. This example permits printing Acme text.

The JSON below is one rule, not a complete document. Put it in your selected custom document’s rules array with structured-rules-v1 and argument-rules-v1 declared, or add it with shield rule add.

{
  "id": "acme-echo",
  "decision": "allow",
  "reason": "Print the Acme fixture",
  "conditions": {
    "domain": "argv",
    "executable": "/bin/echo",
    "arguments": {"kind": "exact", "values": ["Acme text"]}
  }
}
shield __internal run --project /path/to/acme --timeout-ms 5000 -- /bin/echo 'Acme text'

--cwd selects a directory inside that enrollment and outside .shield; otherwise the project root is used. Accepting a proposal through shield policy review publishes its active rule. Ask without a matching native grant exits 3 and deny exits 4 without launching. Ask prints a stored request ID on stderr for operator review. Text-read approvals cannot authorize this command. Invalid state/context/binding or launch failures exit 2 and report their cause. Normal child exits preserve the actual status, including false’s exit 1.

Approve one exact Ask request

After Ask prints a run-request-… ID, inspect and approve it in your terminal, then retry the original command with that ID:

shield request list --project /path/to/acme
shield request show REQUEST_ID --project /path/to/acme
shield request approve REQUEST_ID --project /path/to/acme
shield __internal run --project /path/to/acme --timeout-ms 5000 --approval-request REQUEST_ID -- /bin/echo 'Acme text'

Repeat the original argv, cwd, timeout and supplied --agent, --session-id and --tool-use-id exactly. The selector supplies no authority by itself. Grants bind the project and the literal request; cwd device/ inode or Windows volume/file identity; native executable/loader identities, metadata, digests and verified loader contract; the fixed environment; timeout duration; declared origin; and the private shield-native-run-v1 consumer. The timeout begins afresh with each run attempt; grant expiry is a separate wall-clock limit on consumption. The fixed consumer identifies this CLI boundary across retries, not an authenticated process or user.

Approval reopens and verifies the retained native resources against current Ask policy. The grant also binds the original operator provenance and its minimum issuance record; an issuance retry keeps that original evidence. It cannot override Deny or authorize operator/state mutation, unsupported commands, shell mode or SDK Bash. A registered agent can use request_approve in the same session for a stored checked-run request attributed to that agent. The command’s explicit CLI arguments supply agent/session/tool attribution before capture; these are declared values, not authenticated evidence from a trusted host launcher. Approval preserves those fields, including an unavailable session. The form issues permission only. Retry the original checked command with --approval-request REQUEST_ID, retaining its original attribution and operands. Groups require one identified session; requests without session identity can be reviewed individually. Unattributed CLI requests use terminal approval. The normalized host transport consumes SDK-read grants only. CLI origin fields and operator invocation remain declared evidence; deployment must protect the operator/state boundary. Unrestricted same-user access is outside that boundary.

A pending request waits for your answer however long you take. It closes when you approve or deny it, when the agent session it names ends, or when the project’s 128 requests are full and a new one needs room: the requesting session’s oldest unanswered request goes first, then the oldest of any session. A request without session identity, such as one from the CLI, closes only by an answer or that replacement. A replaced request can no longer be inspected or approved; repeating the command asks again. Approval lasts five minutes, and repeated approval does not renew it. Use shield request deny REQUEST_ID --project /path/to/acme to reject a pending request or revoke an unused grant.

For up to ten minutes after consumption or denial, a compact terminal receipt lets the same operator decision report its recorded outcome without another approval or launch. The separate receipt store holds at most 128 outcomes and evicts older outcomes under pressure. A consumed replay returns no reusable approval material; losing the original result never makes the command run again.

Expired, revoked, consumed, foreign, changed, or stale references cannot launch. A retry with an explicit reference cannot fall back to a later Allow policy. Submit a fresh run without the old selector for fresh review.

The shared writer lock covers revalidation, durable consumption and spawn. Consumption plus minimum authority is published before launch; a publication failure withholds launch, but may already have committed consumption. Launch failure, cancellation, timeout, lost replies and lock-release failure never restore the grant. Inspect its stored status before retrying. Consumption is not execution evidence. History opt-out/purge preserves authority. Each enrollment retains at most 128 native requests. Terminal and expired rows are reclaimed during state updates; reclaimed request IDs are unavailable for inspection or retry. The existing 16 MiB state and 1024 authorization-event limits also apply.

Process ownership and history

The timeout defaults to 5000 ms and accepts 1..3600000 ms, including preparation. Native filesystem calls have no hard deadline. On macOS a running child gets its own process group. SIGINT, SIGTERM and SIGHUP are forwarded to the exact direct child and original group; timeout sends TERM. A child still in that group may receive the signal twice. After a 500 ms grace, KILL escalates even if the direct child has already exited. On ordinary child exit, abort and guard cleanup, KILL stops the direct child and remaining original-group members, even if the direct child moved to another group. The launcher never signals the new group it joined. The launcher observes exit without reaping, reserves the original leader’s PID through final group cleanup, and then reaps that child. It never signals the group after reaping. A separate 500 ms polling window requires direct-child exit and no remaining live original-group members after KILL; an observation or cleanup failure is reported as an execution error, rather than successful completion. Native inspection and reaping can block, so these windows do not provide a hard wall-clock guarantee. Timeout exits 124; cancellation uses 128 plus the supplied signal. The direct child’s actual exit/signal remains separate from that disposition.

This covers the exact direct child and processes that remain in the original group. It does not contain descendants that change process groups or create sessions, launch through another host, or race group inspection with further forks. External processes joining the group and unrestricted same-user interference are outside this ownership contract. The supported leaf commands do not spawn descendants; wider commands remain blocked. Parent SIGKILL or machine failure cannot run cleanup. Descendant zombies are reaped by their parent or the OS, not by Shield.

On GNU/Linux the same Unix process owner retains the unreaped direct child’s PID and original process group. Kernel procfs observations distinguish live group members from zombies, so terminated descendants do not block cleanup merely because the OS has not reaped them. Process-group/session escapes remain outside containment, as on macOS; this does not claim cgroup isolation or parent-death cleanup after SIGKILL.

On Windows the child starts suspended and joins an independently retained kill-on-close Job before running. Normal exit, failure, timeout, cancellation and guard teardown terminate owned Job members and verify that membership becomes empty before releasing ownership. The retained process handle reserves the direct child’s PID. Ctrl-C/Ctrl-Break cancellation exits 130; timeout exits 124. Completion keeps the actual Windows exit code and no POSIX signal. Input/output/error console modes are restored after cleanup. Abrupt launcher loss closes the Job and lets Windows terminate its remaining members. This covers Job descendants; external hosts and privileged interference remain outside ownership.

The launcher holds the project’s writer lock only through verification and spawn, then releases it before history writes and waiting. Child ownership survives post-spawn failures; errors terminate/reap the owned child. Policy changes after launch govern future requests. Inherited file descriptors and shell redirection before Shield starts belong to the invoking host, not this launch boundary.

Default optional history records original policy/binding, handoff disposition, whether spawn occurred, PID and observed exit/signal/completion. CLI attribution remains caller-declared. Completion links the earlier allowed decision only while it remains retained. No stdout/stderr is captured; literal request arguments still follow the existing redaction contract. Opt-out/purge and unavailable history do not change execution permission or child results; failures are reported separately. The project history guide describes inspection and settings.

Native acceptance covers macOS 15.7.9 with x86_64 approval fixtures and AMD64 Windows with MSVC, including exact grant retries, timeout and real Ctrl-Break with console restoration. Other tools, loader configurations, and platforms are unverified. Operator identity is caller-declared.
