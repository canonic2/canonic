The VS Code extension

The Workbench extension runs a local server for each space, shows the sidebar in the Workbench view and the canvas in an editor tab, and connects handoffs and source links to the editor. This page is the reference for its commands and processes.

Activation

The extension serves an open folder that contains workbench.yaml at its root. The file is one space, or several when it lists spaces. In a multi-root workspace, every folder with a workbench.yaml adds its spaces, and the first one shows unless the window last showed another; see Several spaces. A window without one gets no server and no Workbench view, unless you have added spaces. The commands stay available, and say why they can’t run.

Selecting Workbench or running Workbench: Open Canvas opens the tab immediately. It shows Opening Workbench while its server starts and the editor connects to it. Configured services, such as Storybook, start alongside Workbench; their readiness checks do not delay opening the canvas. The page list refreshes when those checks finish. The sidebar shows that it is finding pages during preview discovery. Search becomes available when the list is ready. The canvas shows Loading pages… while reading its pages. Preview loads show Loading preview… after 200 ms if still pending. Later page changes mark the sidebar immediately and keep the previous preview visible for up to 200 ms; a ready replacement appears immediately.

If the server cannot start, the tab says Workbench couldn’t start and points to the Workbench log; reload the window to retry. Closing a loading tab keeps it closed when startup finishes.

Projects in a subfolder

Workbench looks only at the top of each open folder, not inside it. When workbench.yaml lives in a subfolder, such as apps/design in a monorepo, either:

  • open that subfolder as its own window, or
  • add it to the workspace with File › Add Folder to Workspace…, so the rest of the repository stays open beside it.

The folder that holds workbench.yaml, or holds it as .config/workbench.yaml, is the project root: every src, root, and cwd in it is relative to that folder, and the server serves only that folder. See Where the file lives. Implementation code elsewhere in the repository is reached through an implementation’s root, such as root: ../../packages/ui.

Several spaces

One window can switch between several spaces: those described by the workbench.yaml of the window’s folders, which can list several each, and of folders you add from elsewhere on disk. Each space has its own server and port. See Several spaces.

Commands

Command Does
Workbench: Open Canvas Opens the canvas in an editor tab.
Workbench: Open Canvas in Browser Opens the same canvas in your default browser.
Workbench: Copy Canvas URL Copies the canvas address, for a bookmark, a script, or an agent.
Workbench: Refresh Pages Re-reads workbench.yaml and workbench.local.yaml, finds TypeScript previews and defineDocs Markdown pages again, and refreshes the sidebar and canvas. This happens automatically when either YAML file changes, and when a *.workbench.ts file is added, removed, renamed or retitled.
Workbench: Switch Space… Lists the spaces and shows the one you pick.
Workbench: Add Space… Adds a folder with a workbench.yaml to the spaces and switches to it.
Workbench: Show Log Opens the Workbench output log.

Open Canvas in Browser and Copy Canvas URL use the current space.

The server

Each space gets its own server:

  • It listens on 127.0.0.1 only. It serves your project folder, so nothing outside your machine can reach it.
  • It uses port 3579, then 3580 to 3583, then any free port the system offers. With several windows or spaces running, each space gets the next free port, in the order the servers started.
  • It serves the project at / and the workbench at /_workbench/ on the same origin, which is what lets the workbench read and capture the live page.
  • It adds one preview-compat.js bundle to served HTML and managed previews. See How pages are served.

Workbench: Copy Canvas URL gives the actual address.

The browser runtime

Screenshots, handoffs, design-system exports and the canvas’s background images come from Workbench’s browser runtime, a Chromium (CEF) that Workbench starts and owns. It is shared by every space in the window and stays running until the extension stops, so screenshots are fast:

  • It keeps an inert, scriptless copy of the page you’re viewing up to date in the background. See How screenshots are taken.
  • It renders the background images and static copies that artboards you aren’t running show on the canvas in a second runtime process, started when first needed, at a lower priority so your other apps stay responsive.
  • Pages are windowless: it shows no window, and on macOS no Dock icon.
  • The first time it’s needed, the runtime is unpacked into ~/.canonic-workbench/runtime/, next to the bundled Node (see below). The first screenshot after an update can take longer while it is unpacked.
  • If it crashes, the next screenshot starts it again and restores the latest view. If a page stops answering, that page is closed, and the page is loaded again the next time it’s needed.

Your project’s code (computed definitions, workbench.config.ts, Astro and Vue pages) runs on the Node 24 the extension ships, so you don’t need Node installed. The first time project code runs, Workbench unpacks that Node into ~/.canonic-workbench/runtime/, which every Workbench version on the machine shares; set CANONIC_WORKBENCH_HOME to use another folder. That first run takes a few seconds longer. A copy that no running Workbench uses and none has used for a week is removed the next time Workbench unpacks one.

If your project needs its own Node, for example because its native addons are built for it, name it in workbench.local.yaml; it must be Node 24 or later:

# workbench.local.yaml
node: /usr/local/bin/node

A path that doesn’t exist, or a Node older than 24, stops project code with an error naming this setting.

Screenshots need the browser runtime. This release ships it only in the Intel macOS (darwin-x64) .vsix, and it needs macOS 15 or later; the other platforms’ packages don’t include it. Without it, or if it can’t be unpacked or started, the camera and Copy handoff show the reason instead of a screenshot (for example, “Screenshots need Workbench’s browser runtime, and this copy of Workbench has no browser runtime for linux-x64.”), a design-system export lists the missing reference screenshots as warnings, and the canvas shows placeholders for artboards you aren’t running.

The preview compiler

The server compiles TypeScript previews and docs examples itself. Project JavaScript that has to run while they build runs in a separate Node process, the evaluator: definitions that compute their values, workbench.config.ts, JavaScript loaders from its rules, Vue single-file components, and Astro rendering. Packaged builds run the evaluator on the bundled runtime, so it doesn’t need a separate Node installation.

  • The compiler builds previews and docs examples when you open them, reuses its compiled modules for later pages, and stops with the server.
  • The evaluator starts the first time a build needs it, and stops with the server. A space whose definitions are plain values and that has no workbench.config.ts never starts one.
  • If the evaluator stops, the next build that needs it starts a new one.
  • Changing the previews key in workbench.yaml replaces the compilers with new ones that use the new settings. With previews: false, nothing is compiled and no evaluator runs: docs show their Markdown, and each example panel says why its example is missing.

Logs

Errors from the canvas, the browser runtime, the preview compiler, the server, and handoffs are written to the Workbench output log. Run Workbench: Show Log to open it.

  • VS Code manages the log and its retention. Nothing is written to your project.
  • Each server stops logging after 2 MB in a session.
  • Entries contain event details and errors only, never screenshots, page HTML, or handoff prompts.

Workspace trust

Workbench doesn’t declare support for untrusted workspaces, so VS Code doesn’t run it in Restricted Mode. Trust the folder to use it. Trusting a folder lets Workbench run start commands, which are shell commands from workbench.yaml, and TypeScript previews and docs page examples, which run project code.

Files and network access

In your project, Workbench writes only:

  • .canonic/.handoffs/, the screenshots that Copy handoff saves. Add it to .gitignore.
  • workbench.yaml, when you save Configure pages.

Outside the project:

  • The camera’s screenshots go to your browser’s or editor’s downloads folder.
  • The bundled Node and browser runtime are unpacked into ~/.canonic-workbench/runtime/.
  • The browser runtime’s page profiles go into the extension’s storage in your editor’s user data folder (globalStorage). A standalone server uses the system’s temporary folder instead.
  • The log is kept by VS Code. See Logs.

Network access:

  • The server listens on 127.0.0.1 only, so other machines can’t reach it.
  • The extension sends no telemetry and downloads nothing at runtime. The runtime it needs ships inside the .vsix.
  • The canvas loads what you point it at: your own pages and their assets, URL implementations, and Storybook. Implementations load through a proxy on 127.0.0.1 that adds the preview bridge to their pages. If the bridge hasn’t connected, the browser runtime loads a lens’s URL itself to capture it.
  • url: auto probes local ports for a running Storybook, and start commands probe the check and ready addresses you configure.
  • A handoff goes only to your clipboard and .canonic/.handoffs/. Nothing is sent to an agent until you paste it.

Updating

An install from the Visual Studio Marketplace updates like any other extension. For an install from a .vsix, download the newer .vsix from the latest release and install it the same way as the first one; it replaces the installed version. To switch a .vsix install in VS Code to Marketplace updates, uninstall it and install Canonic Workbench from the Extensions view.

Then run Developer: Reload Window in each open project window. Installing replaces the files on disk, but running windows, servers, browser runtimes, and preview evaluators keep the old code until their window reloads. Reloading the canvas or running Refresh Pages isn’t enough.

Uninstalling

Uninstall Canonic Workbench from the Extensions view, or from the terminal:

code --uninstall-extension canonic.canonic-workbench

Then reload any window that had a project open, to stop its server and helpers. Uninstalling leaves your projects as they are; to remove Workbench’s files from a project too, see Removing Workbench from a project.

Running without VS Code

The extension’s server runs on its own, started with Node 24 or later. Find the installed extension’s folder and point the server at a project:

node ~/.vscode/extensions/canonic.canonic-workbench-*/server/node/server.js path/to/project

It prints workbench on http://127.0.0.1:3579/_workbench/ (or the port it got). Open that address in a browser. Without a project argument, it serves the current folder. Give it several folders to switch between their spaces in the browser; see Several spaces. Stop it with Ctrl+C.

The folder name ends in the version and platform, such as canonic.canonic-workbench-0.7.0-darwin-arm64. On Windows, extensions are in %USERPROFILE%\.vscode\extensions. Cursor, Windsurf, and other forks keep extensions in their own folder, such as ~/.cursor/extensions.

What works where:

VS Code, or Open Canvas in Browser server/node/server.js in a browser
Pages, scenarios, sizes, zoom Yes Yes
Lenses Yes Yes
TypeScript previews Yes Yes

Annotations and camera Yes Yes

Platform support

Desktop macOS is the most exercised platform. Windows and Linux builds, remote workspaces (SSH, containers, WSL), and other platforms have had less validation. A remote workspace runs the extension on the remote machine, so install the .vsix built for that machine’s platform, and on a Linux host without a display, screenshots aren’t available. Browser-only VS Code, such as vscode.dev, can’t run the local server or browser runtime.

Release builds are unsigned.
