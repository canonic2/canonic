Developing Shield

Shield is one Cargo package (canonic-shield), library shield, and executable shield. Rust nightly-2026-11-09 (rustc 1.102) is pinned with rustfmt, Clippy and llvm-tools. Cargo.lock owns dependency versions; there is no root Cargo workspace. The package’s own workspace adds only the xtask crate, which holds the development tasks that are more than one Cargo command; cargo xtask --help lists them.

Fast iteration

From this package directory, where rustup selects the pinned toolchain:

cargo build --locked
cargo nextest run --locked --lib 'policy::'
# Select integration tests explicitly when needed:
cargo nextest run --locked --test integration 'selected_test_name'

cargo build writes an incremental build to target/debug/shield; run it directly to try changes. Give nextest a substring filter, with --lib for library tests. Replace the integration example’s placeholder with a real test name; nextest fails if nothing matches.

For a pack-add timeout, run the five-second MCP regression with an immutable public pack artifact. The fixture copies its rules into test-owned releases; it never modifies the artifact or an enrolled project:

SHIELD_PACK_PROFILE_ARTIFACT=/path/to/pack.yml cargo nextest run --locked --lib development_pack_proposals_complete

Keep target/ between iterations to reuse Cargo’s cache. Use release builds for performance measurements.

To check container shell policy against the published Docker and baseline artifacts, pass the registry checkout’s public/ directory to the focused fixture. It reads pack files and previews policy decisions without running Docker.

SHIELD_DOCKER_TEST_REGISTRY=/path/to/shield-registry/public cargo nextest run --locked --lib --run-ignored ignored-only published_docker_and_baseline_packs_preserve_container_policy

To check the in-place upgrade of a pre-continuity checkpoint written by a separately retained executable:

SHIELD_PREVIOUS_BINARY=/path/to/previous/shield cargo nextest run --locked --test integration --run-ignored ignored-only previous_binary_unreceipted_checkpoint

This opt-in fixture initializes through that previous binary in an isolated project and home. It verifies that status reports the pending upgrade without changing the record, and that the first ordinary command keeps the project ID, converts the checkpoint once to runtime state without a copy of the policy, and that later reads leave it unchanged. The supplied binary must predate the policy-files format.

Native Linux development

GNU/Linux builds support x64 and ARM64 with the pinned Rust toolchain, a GNU C compiler and ordinary Unix file permissions, terminal leases and native hooks. Shield includes MCP Kit, Registry Kit and TUI Kit; Process Kit is not used. The CLI needs no Node installation. Interactive commands require terminal stdin/stdout and a cursor-capable TERM; hooks and MCP stdio remain noninteractive.

From this package directory, cargo build --locked builds target/debug/shield. The distribution helper additionally requires Python 3.11+ and GNU binutils:

python3 scripts/release-linux.py build --architecture x64
python3 scripts/release-linux.py package --architecture x64

Outputs are target/x86_64-unknown-linux-gnu/release/shield and dist/shield-<version>-x86_64-unknown-linux-gnu.tar.gz, with a .sha256 sidecar. CARGO_TARGET_DIR selects another build directory; --output-directory selects another package directory. Existing archives/checksums are refused. The helper remaps publisher paths in Rust/C code, checks the ELF architecture and scans the binary for publisher paths before accepting a build. Clear custom Rust/C flags before using it. Package after rebuilding changed code or dependencies.

For a cross-build from x64, install an aarch64-linux-gnu-gcc cross-compiler and its GNU target libraries, then add the pinned Rust target:

rustup target add --toolchain nightly-2026-11-09 aarch64-unknown-linux-gnu
python3 scripts/release-linux.py build --architecture arm64
python3 scripts/release-linux.py package --architecture arm64

An ARM64 Linux host can build that target with its native C compiler. Cross-builds do not establish native ARM64 acceptance. The packager includes Canonic’s license, resolved normal/build dependency notices and Rust standard-library notices. It normalizes archive ownership and indexes notices in BUILD.json, alongside the executable checksum, versioned glibc symbol requirements and a conservative minimum glibc baseline at least as new as the selected compiler’s target libc. The helper locates libc.so.6 through that compiler, checks its architecture and reads its release version without executing it. An unavailable or unrecognized target libc refuses the build, including cross-builds. These are workspace candidates without source-revision attestation.

Linux installation and compatibility

Extract the archive, then copy its shield executable to a stable folder on PATH, for example ~/.local/bin/shield, with mode 755. Check shield --version and follow Your first Shield project. Close Shield and connected agents before replacing the executable. Updates at the same installed path keep existing registrations; moving the executable requires setting up the registered agents again with shield mcp setup --agent <agent>. To remove an installation, run shield mcp remove for each connected agent in each project, then delete the executable. Preserve project .shield folders to retain policy and history.

The GNU executable’s minimum glibc version depends on the target toolchain and is recorded in BUILD.json. Build on the oldest intended supported GNU system to target older hosts; a successful build on a new Ubuntu release does not prove compatibility with older distributions. The bounded native runner additionally requires a supported glibc 1.1 loader cache, readable kernel procfs, protected system images and the exact commands in native execution. Musl-only hosts are outside this GNU build target.

Linux compatibility completion is owner-accepted for this stage with focused x64 checks and other behavior assumed from the shared Unix implementation. Full package suites, live Claude/Codex sessions, additional distributions and ARM64 build/runtime acceptance are not claimed. Signing and publication remain separate distribution work; these scripts perform neither.

Native Windows development

Use the pinned MSVC Rust toolchain and Visual Studio C++ build tools. From this package directory in a Windows developer terminal:

cargo build --locked
cargo test --locked --lib windows_opaque_shells_never_use_allow_fallback

Run strict native lint separately with cargo clippy --locked --all-targets.

The development binary is target/debug/shield.exe. Windows acceptance covers AMD64 source builds, enrollment, setup/repair/removal, native console ownership, private ACLs, MCP stdio, and Registry installation/offline reproduction. Claude Code 2.1.312 file and PowerShell tools pass Allow/Deny/Ask and missing/timeout-hook checks with an isolated local provider. Codex 0.166.0 loads the generated project hooks: native command Allow/Deny, configured Ask allowance and prefix-covered Ask blocking pass with retained Shield decisions. Unsupported PowerShell source is also withheld by the generated hook.

To prepare an AMD64 release binary from the same developer terminal, run:

powershell -NoProfile -File scripts/build-windows.ps1

For ARM64, install the Visual Studio C++ ARM64 tools and ARM64 Windows SDK libraries, add the pinned Rust target, and use an MSVC developer terminal targeting ARM64 (for example, the x64_arm64 Cross Tools Command Prompt):

rustup target add --toolchain nightly-2026-11-09 aarch64-pc-windows-msvc
powershell -NoProfile -File scripts/build-windows.ps1 -Architecture arm64

An x64 Windows host can cross-build ARM64; it does not need to run the ARM64 executable. Native ARM64 development hosts can use an ARM64 developer terminal. Both builds include MCP Kit, Registry Kit and TUI Kit. Process Kit is not used.

The outputs are target/x86_64-pc-windows-msvc/release/shield.exe and target/aarch64-pc-windows-msvc/release/shield.exe, respectively. The checked-in release configuration requests static C runtime linkage for Shield and its dependencies. The script adds neutral source/cache diagnostic paths through a private temporary Cargo configuration, then runs the cargo build-windows or cargo build-windows-arm64 alias. It checks the MSVC terminal’s target architecture and the resulting executable’s PE architecture. It refuses Rust flag overrides that would replace the verified build settings. The explicit target keeps those flags away from host build scripts and procedural macros. Inspect the executable’s imported DLLs with dumpbin /DEPENDENTS before distributing it; the development build uses the toolchain’s default runtime linkage.

Verify the built executable in a temporary installation with spaces in its path:

$env:SHIELD_WINDOWS_RELEASE_BINARY = Join-Path (Get-Location) 'target\x86_64-pc-windows-msvc\release\shield.exe'
cargo test --locked --test integration windows_release_binary_runs_from_owned_installation -- --ignored

This checks startup, confirmed offline enrollment, replacement after exit and removal while preserving the enrolled project. It verifies the portable binary; package-manager installation and migration between released versions need their own acceptance.

Portable Windows packages

After building, optionally Authenticode-sign and timestamp shield.exe, then package that final executable from the same checkout and toolchain:

powershell -NoProfile -File scripts/package-windows.ps1 -Architecture x64
powershell -NoProfile -File scripts/package-windows.ps1 -Architecture arm64

Each command writes dist/shield-<version>-<Rust target>.zip and a .sha256 sidecar. -OutputDirectory C:\Acme\shield-candidates selects another directory; existing outputs are refused. CARGO_TARGET_DIR, when set, selects the same build directory for both scripts. The packager checks the binary architecture, includes the product license, resolved normal/build dependency notices and Rust standard-library notices, and indexes them in BUILD.json. Package metadata describes a workspace candidate with no source-revision attestation; it is not proof of a clean source checkout, a signature or native acceptance. Build again after source or dependency changes before packaging.

The scripts do not sign or publish anything. Sign before packaging and compute checksums after signing. ARM64 build/package execution has not been verified; its implementation is accepted for this stage without native runtime acceptance.

To install a portable package, extract it into a stable folder you own and add that folder to PATH. Check shield --version, then follow Your first Shield project. Before an update, close Shield and connected agents, replace the executable at the same installed path, and restart the agent. After moving the installation, set up its registered agents again with shield mcp setup --agent <agent>. To remove it, run shield mcp remove for each connected agent in each project, then delete the installation folder. Preserve project .shield folders to keep policy/history.

Supported Windows commands and acceptance

The Windows parsers admit literal native calls to git, rg, node, rustc, cargo, make, just and shield, preserving each literal executable for policy. PowerShell supports non-expanding quotes, semicolon/newline sequences and the literal call operator &. Cmd supports & sequences and &&/|| chains; apostrophes stay literal there. Empty arguments, embedded quotes, ambiguous trailing backslashes, expansions, redirections, cmdlets, batches and unverified explicit shell overrides remain outside coverage. PowerShell chain operators remain unclassified without a trusted version/mode contract. Reported versions are retained as evidence and do not grant more syntax. Native handoff blocks unclassified source, including when Ask fallback allows ordinary policy Ask requests. Extended Windows sequence/cmd acceptance needs a separately scoped native target; portable parser/hook fixtures do not establish it. The checked native runner also supports three bounded System32 leaf forms on AMD64 and ARM64 Windows, requiring matching native PE images. Native AMD64 acceptance covers Allow/Deny/Ask, exact one-time grants, replay refusal, timeout, Ctrl-Break and console restoration. Checked Git inspections support a protected Git for Windows 2.56.0.windows.3 ucrt64 installation on AMD64, or clangarm64 installation on ARM64. Native AMD64 acceptance covers helper suppression, index preservation, exact grants and refusal of wrappers, local copies and unsupported argv. ARM64 checked execution uses the same ACL, held-image, grant and Job contracts; it refuses foreign-architecture executables/DLLs, including x64 Git under emulation. ARM64 runtime behavior is assumed working for this stage, not tested. There are no published Windows installers or native ARM64 acceptance results.

The ignored native-host fixtures need Node 24+, Git for Windows and isolated copies of Claude Code 2.1.312 and Codex 0.166.0. Install the pinned CLIs in an owned directory outside the Windows temporary folder, then point SHIELD_WINDOWS_AGENTS_ROOT at it:

npm install --prefix C:\Acme\shield-agent-tests --no-save @anthropic-ai/claude-code@2.1.312 @openai/codex@0.166.0
$env:SHIELD_WINDOWS_AGENTS_ROOT = 'C:\Acme\shield-agent-tests'
cargo test --locked --test integration windows_agent_hosts_load_native_hooks_against_local_providers -- --ignored
cargo test --locked --test integration windows_agent_hosts_codex_loads_native_hooks_against_local_provider -- --ignored

Run these host checks separately. They use private ConPTY sessions, temporary projects/profiles and scripted loopback providers. They make no external model requests and do not change your ordinary agent profile. The public fixtures include their provider implementation; no private SDK test package is needed.

With the protected Git version above installed in the default Program Files location, run its isolated repository acceptance separately:

cargo test --locked --test integration windows_git_inspections -- --ignored

CLI and MCP map their inputs into shared review operations. History queries use an application-owned query type; pack operations expose direct list, show, search, info and preparation functions. Shared owners can read files and acquire registry artifacts, including retaining verification checkpoints, without opening a terminal. CLI prompts and host confirmation run before calling the common publication workflow. MCP retains its own paging, diagnostic handles and response projection.

The policy core performs no filesystem I/O and contains no command permission tables. Packs and custom rules supply permissions; location/ supplies fresh request facts. Shell analysis uses submitted source and available context, without attesting execution.

build.rs checks any bundled skill folders under skills/ and calls canonic-mcp-kit’s documentation build helper, which validates every guide under docs/ and writes one compressed bundle to OUT_DIR. An invalid guide, such as a symbolic link or a page that is not UTF-8, fails the build with its relative path.

The canonic-registry-kit dependency handles registry identity, authentication, acquisition, checkpoints, resolution, and UTC timestamps. Shield owns pack declarations and the review that writes acquired artifacts into the policy. canonic-mcp-kit handles framing, lifecycle, validation, cancellation, deadlines, and confirmation requests; Shield’s handler supplies its tools and limits. Its documentation module also supplies the docs_* tool definitions and queries; src/review/mcp/documentation.rs embeds the bundle and maps the library’s failures into Shield’s result envelope.

Agent adapters translate vendor payloads and setup formats. They cannot bypass core policy or approval checks. To add an agent, implement its adapter and registry entry, then verify payload mapping, setup, and real host behavior. CLI detection belongs in the adapter’s is_installed method; it inspects PATH without starting the tool.

adapters/ contains private Node 24+ ESM modules: process-transport/ handles subprocess I/O and cancellation, enforcement-response/ validates receipts, and claude-read-only/ maps SDK callbacks. adapters/sdk-tests/ pins the SDK dependencies. Rust integration tests share tests/integration/main.rs.

Check tools

Install the developer tools:

cargo install --locked cargo-nextest@0.9.146 cargo-deny@0.20.2 cargo-llvm-cov@0.9.1 cargo-insta@1.49.0 cargo-sweep@0.8.0

Tests use assert_cmd, assert_fs, predicates, insta, and proptest. Tool versions and dependencies are pinned in the package configuration.

The retained interceptor’s protocol regression runs with the Rust library tests. Its JavaScript receipt-validator interoperability check is opt-in and requires Node 24+:

cargo nextest run --locked --lib --run-ignored ignored-only historical_interceptor_receipts_pass_legacy_js_validator

Checks

The default nextest profile runs four tests at a time. Run process-heavy Node, SDK and Rust suites separately so fixture startup does not compete across runners. Do not rebuild a shared executable while installation fixtures run: registrations pin its digest, and replacing it changes the fixture’s protection diagnostics. In an agent sandbox, request host access before running integration checks: PTY fixtures need controlling terminals and process signals, HTTP/TLS fixtures need loopback listeners, and cargo-deny needs its advisory cache. A sandbox permission refusal requires the same check with host access; product policy changes cannot grant that access.

Run the Make targets below from this package directory, where rustup selects the pinned toolchain.

cargo test --locked also runs the behavioral tests. cargo llvm-cov nextest --locked produces a coverage report; it is not a coverage threshold. Cargo nextest, deny, and llvm-cov are optional developer tools installed separately. Use ~/.cargo/bin/cargo when Cargo is not on PATH and --offline only with a populated dependency cache.

From this package:

cargo build --release --locked
npm --prefix adapters test
npm --prefix adapters/sdk-tests test

cargo xtask install installs into ~/.local/bin, ad-hoc signed on macOS; --prefix DIR selects another root, and Cargo options after -- reach cargo install, such as cargo xtask install -- --offline to use cached dependencies.

Generated Copilot/OpenCode acceptance on the selected Mac

The opt-in generated-callback fixture uses installed Copilot CLI 1.0.105 or OpenCode V1 1.14.27, disposable projects and one isolated test-process home. Inspect the installed version/offline contract first without building Shield or starting a provider:

cargo xtask native-preflight --host copilot
cargo xtask native-preflight --host opencode

A different version, missing offline route or missing CLI is a prerequisite failure, not a reason to install or silently try a cloud provider. Once that preflight passes, select one host:

cargo xtask native-acceptance --host copilot
cargo xtask native-acceptance --host opencode

Each command builds the development binary without installing it, then checks the generated project registration using native file reads for Allow, Deny and Ask. Copilot disables the Shield MCP server through its documented client option for these focused file-hook cells, leaving generated hooks active; this avoids loading the unrelated MCP tool catalog into the fixture model’s context budget. It does not establish MCP tool acceptance. Copilot Ask is checked as withheld in noninteractive prompt mode; OpenCode uses its reviewed standing Deny fallback, not native Ask. Provider tool results and Shield history independently establish the observed outcome. The OpenCode target also attempts a later plugin argument mutation and requires evidence that it actually ran after Shield before attributing the refusal to frozen arguments.

To reproduce against an already retained executable while other source work is in progress, add --binary with that executable’s absolute path to the same cargo xtask native-acceptance --host command. It then does not compile or install code. Record that executable’s SHA-256 with the result and preserve it for the entire run; its result describes that binary, not later source edits. Optional --filter selects a named native case when reproducing a failure.

These targets need an owned loopback listener, operator-confirmation PTYs and TERM/KILL of their owned child process groups. Native children inherit an explicit credential-free environment, dummy provider keys, local-only provider selection and the pinned host’s update/telemetry/fetch disable flags. They do not read a real account profile or publish global registrations. Environment and provider configuration are not OS network confinement; no such isolation claim is made. A host without the established local-only route must not run the acceptance cells. Native children have a 40-second deadline, bounded output and kill/reap cleanup. Run targets separately from Cargo checks and other native campaigns; do not replace the binary while registrations pin it.

The fixture is excluded unless this explicit target selects its host, so the ordinary SDK suite does not add this native campaign. Prepared fixtures alone are not installed-host acceptance evidence. Interactive Ask acceptance/cancel, other platforms, OpenCode V2 and hook/plugin startup failure protection remain separate targets and limits.

Run Cargo through rustup, from this package, so it selects the pinned toolchain; use ~/.cargo/bin/cargo when another Cargo comes first on PATH.

Debug builds and diagnostics

cargo build --profile diagnostic --locked builds target/diagnostic/shield with release optimization, debug symbols, debug assertions and automatic JSONL logging. Native hook deadlines also apply to diagnostic builds. cargo xtask install -- --profile diagnostic installs that build into ~/.local/bin. cargo xtask install installs the release build, which has logging disabled by default. Replacing the installed executable at the same path keeps existing registrations; restart the agent to load the new build.

Automatic logs live in the OS temporary directory under shield-logs/shield-<timestamp>-<pid>.jsonl. On macOS, inspect them with ls -lt "${TMPDIR%/}/shield-logs". Each native hook gets its own file; the MCP server keeps a file for its process lifetime. Operator commands print their log path on stderr. Native hooks and MCP omit that startup message so protocol output and ordinary agent feedback remain clean.

MCP frame logging uses a separate worker with an eight-frame queue. The dispatcher submits frames without waiting for parsing or file writes; a full queue drops diagnostic frames. Tool names are cached once per process. The logging worker drains accepted frames with a 5 ms shutdown allowance. An unfinished drain or dropped frames produce a diagnostic stderr warning. Slow storage does not block live ping or cancellation dispatch. Frame sizes remain bounded by the MCP input and output limits. Frame records include observed_us, captured when the observer receives the frame, before worker parsing or file writes.

Both builds accept --debug-log-dir DIRECTORY to enable logging into another directory and --no-debug-log to disable it. SHIELD_DEBUG_LOG_DIR also selects the directory for child processes that inherit it; export it before starting the agent. Hosts can filter child environments. The CLI directory overrides the environment, and opt-out overrides the environment and debug default. Shield uses a directory rather than a single file because concurrent native callbacks start separate processes.

Files are uniquely created, use mode 0600 on Unix, and stop at 8 MiB with a limit marker. Startup admission keeps Shield-owned logs within 32 files and 256 MiB, reserving each live writer’s full allowance and reclaiming oldest completed logs. Live writers and unrelated files are preserved; exhausted capacity disables optional logging. A logging failure reports a warning on stderr and disables logging without changing authorization or transport output.

Records include elapsed milliseconds and PID/version/build type, native agent/event/tool and session/turn/tool-call IDs, captured input bytes, input validity and overflow, project/snapshot preparation, evaluation, native handoff and history stage timings, policy decision/fallback/disposition, completion history status, response event/decision/context shape, and MCP method/tool/ID, request/response sizes and error status. Commands, arguments, tool results, policy content, project paths, credentials and raw error text are omitted. Large truncated hook input cannot supply parsed IDs; its overflow and captured size are still recorded. Pair input/output records by PID and MCP messages by request ID to inspect timing. These logs are diagnostic evidence, separate from request history and execution attestation. RUST_BACKTRACE=1 enables panic backtraces on stderr; debug symbols also support native debuggers.

Request trace records add monotonic microsecond offsets, a wall-clock anchor, connection/request/trace IDs and fixed stage names. request_span durations are inclusive of child spans; do not sum nested durations into a request total. request_end reports work counters, outcome and total handler duration. Counters initialized to zero name instrumented work; absent counters have no reported observation and must not be interpreted as zero. request_incomplete means a request link was dropped without completion, not that its mutation rolled back. Fixed events and request records share a nonblocking queue capped at 512 records of at most 32 KiB each. Loss appears as dropped_records, dropped_records_total, dropped_spans or a diagnostic stderr warning. Operator/MCP writer shutdown waits at most 5 ms before reporting an unfinished drain. Native callbacks retain fixed hook-stage events without creating request spans or waiting for an exit drain; recent events may be lost at process exit. Disabled logging does not construct event fields.

The apply trace covers validation, policy preparation, writer-lock wait, file writes, connection publication and durable sync operations. Legacy form continuations retain their request link and measure the input or approval wait. Host permission obtained before Shield receives an MCP call is outside this measurement. The handler boundary also excludes MCP scheduler queueing, schema validation and final wire encoding; round-trip tests measure transport overhead separately. Modern form retries have separate traces. Proposal spans distinguish base capture, edits, next capture, comparison, plan preparation, handle reservation and presentation. policy.source_captures counts source validation independently of compiled-plan preparation, so re-parsing packs cannot hide behind a zero preparation count. A process validates each exact set of policy sources once: following the files, comparing them and rebuilding a proposal’s two sides reuse the snapshot of the same bytes, counted by policy.source_capture_reuses. Changed bytes, and sources that failed, are validated again. Pack spans distinguish decoding, source validation, resolution and matcher preparation. pattern.compiled and pattern.reused count newly built and exact reused matcher programs. Rule/access-path proposal edits borrow matchers from the preceding captured snapshot, while validating source and accounting the new store’s pattern bytes normally. Fresh compiled plans check their encoded layout and retain source validation from typed construction, avoiding duplicate decoding and semantic validation of just-encoded records. Untrusted full-image admission remains covered separately by compiled-policy tests. handle.retain and source.identity spans expose handle admission and canonical candidate hashing. handle.admission_encodings counts new-handle size measurements; cached handles skip them. source.identity_encodings counts candidate-identity encodings, and cursor.rows_copied counts rows projected into a page. Shared JSON size checks count encoded UTF-8 bytes without retaining an output string; source hashing uses bounded scratch space and preserves existing compact-JSON digests.

Run the focused development regression with cargo nextest run --locked --lib --success-output immediate apply_request_trace_explains_work. It creates an isolated project, proposes and applies three batches through real stdio, and prints timings and work counts. Production state readers select authority metadata, current source, one proposal or optional history explicitly.
